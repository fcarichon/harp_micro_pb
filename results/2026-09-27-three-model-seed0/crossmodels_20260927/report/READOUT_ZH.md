# 三模型实验最终解读

2026 年 9 月 27 日：Qwen、Gemma 和 Llama 各自的 60 组配置已经全部完成，总计 180 组。所有结果通过结构、配置和分析检查；Gemma、Llama 各 720 次生成的诊断也全部通过。原始结果、日志和版本信息已保存，Qwen 基线没有改动。没有重跑无效投票来改善结果，也尚未上传 GitHub 或联系 Florian。

## 最重要的结果

箭头表示讨论前 → 讨论后。每个模型每阶段有 180 张投票，配置层面有 60 个结果。

| 指标 | Qwen3-30B-A3B | Gemma-4-31B | Llama-3.1-8B |
| --- | ---: | ---: | ---: |
| 有效投票 | 180/180 → 180/180 | 180/180 → 179/180 | 178/180 → 179/180 |
| 三个 agent 完全一致 | 0/60 → 8/60 | 0/60 → 15/60 | 1/60 → 4/60 |
| 聚合出可行的两项目方案 | 37/60 → 52/60 | 31/60 → 58/60 | 46/60 → 48/60 |
| 最终条件平均归一化福利 | 0.946，n=52 | 0.968，n=58 | 0.927，n=48 |
| 前后都可行的配置中，福利平均变化 | −0.026，n=35 | +0.010，n=30 | −0.040，n=38 |

本轮观察中，Gemma 最容易在讨论后产生可行的聚合结果，也有最多的完全一致；Qwen 也有明显的可行性提升；Llama 的净提升较小。不过，这不是一个严格控制条件后的模型能力排名。

## 三个容易混淆的地方

**1. 有可行方案，不等于三个 agent 达成共识。** Gemma 的 58/60 是聚合规则能输出两个有效项目，而不是 58 组完全一致。它真正完全一致的只有 15/60；Qwen 是 8/60，Llama 是 4/60。实验必须分别呈现这两个指标。

**2. 讨论后总体可行率上升，不等于每一组都改善。** Gemma 有 28 组从不可行变可行，1 组反而失去可行性；Qwen 是 17 组改善、2 组失去可行性；Llama 是 10 组改善、8 组失去可行性。Llama 的 46→48 因此掩盖了较多前后变化。进一步看前后都可行的 38 组，Llama 的福利是 2 组提高、11 组下降、25 组不变。没有额外的无讨论对照实验，不能仅凭前后差异断言讨论的因果效果。

**3. 福利均值只统计最终可行的结果。** 表中的 n 不同，三模型不是在完全相同的一批成功配置上计算均值。不可行结果没有被当成福利 0，也没有消失于可行率统计。前后福利变化又只统计前后都可行的子集，不能用它替代全部 60 组的表现。

## 仍然值得和 Florian 一起看的问题

- Gemma 的全部 360 张投票都带 Markdown 代码围栏。原解析器允许这种格式，因此“有效投票”不代表“严格按要求只返回 JSON”。`RFQ_optimal` 的 final A1 连续给出两个 JSON 答案，原解析器拒绝了这个结果。它在 491/512 tokens 处正常结束，不是被截断。
- Llama 有两张初始投票重复选择 `P14`，另有一张最终投票的 JSON 字符串包含未转义换行。它的 359/360 张投票是严格 JSON，但只有 357/360 张是有效投票：格式正确和决策符合约束是两回事。
- Llama 在 `EGQ_optimal` 的一条讨论中提出了三个项目，而不是两个；该组最终投票却有效。这说明最终投票合法并不足以证明整个讨论过程都遵守规则。
- Gemma、Llama 各 720 次生成都正常以 EOS 结束，没有撞到 token 上限，也没有空输出或模型响应处理错误。Qwen 当时没有记录同样的逐次生成诊断，所以不能给它补报“截断率为零”。

这些问题都已经保留在结果中，没有修改原始输出、放宽解析器或重跑。

## 如何理解模型之间的差别

三模型使用相同的 60 组配置和原始提示内容，每组都只有 seed 0；temperature=0.7、top-p=0.9、max-new-tokens=512。模型规模、架构、原生对话模板和分词方式不同，而且没有被显式覆盖的 top-k 也不同：Qwen 为 20、Gemma 为 64、Llama 为 50（由库默认值补齐）。详细核验见 [后端可比性说明](BACKEND_COMPARABILITY.md)。

所以目前能说的是“在本轮设置下观察到这些差异”，不能说“大模型一定更好”“Gemma 显著优于其他模型”，也不能把 60 个不同配置当成同一条件的 60 次重复实验。

## 下一步适合讨论什么

现在已经有足够材料一起审核，不需要因为出现无效投票或不一致就继续重跑。建议先和 Florian 确认：benchmark 的主要目标究竟是全体共识，还是多数投票能产生可行方案？然后一起看讨论后失去可行性、福利下降、格式出错的具体例子，再决定下一轮优先加多个 seed、无讨论对照，还是统一更多生成设置。这些是下一轮的候选方向，并未自动启动。

原始数据和版本记录与分析一并保留。这份公开结果包供异步讨论，明确标注为单 seed、不同规模和原生后端的描述性结果。文首未上传的说明记录了 9 月 27 日实验完成时的状态；本次后续分享见结果包 README，不包含 Slack 发送。
